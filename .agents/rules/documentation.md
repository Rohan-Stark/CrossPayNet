# Documentation Rules

## Architecture & Decisions
* **Architecture Docs**: High-level system design documents belong in `docs/architecture/`.
* **ADRs**: Architectural decisions MUST be documented using the ADR template and stored in `docs/decisions/`.

## Domain & API
* **Domain Knowledge**: Business rules, domain models, and ubiquitous language definitions belong in `docs/domain/`.
* **API Documentation**: API contracts, Swagger/OpenAPI specs, and integration guides belong in `docs/api/`.

## Operations & Learning
* **Operations**: Runbooks, deployment guides, and observability dashboards documentation belong in `docs/operations/`.
* **Learning Notes**: Educational notes on concepts like SWIFT, ISO 20022, and distributed systems belong in `docs/learning/`.

## General Expectations
* Use Markdown consistently.
* Follow clear naming conventions (e.g., `ADR-001-Decision-Name.md`).
* After any major architectural change, relevant documentation must be updated or created.
